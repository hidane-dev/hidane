# Client compatibility

Which clients can talk to hidane depends on the transport each SDK uses when it is pointed at an
emulator. Phase 0 read the SDK sources to settle this; the conclusions are below. The status
column says what `main` does today: **verified** means the client's results were compared with the
official emulator's (`results/`) for everything it is expected to do; **partially verified**, for
some of it; **not verified** means hidane serves its transport but nobody has run that client
against it yet. The statuses come from the
[SDK certification matrix](sdk-certification.md), generated from the recorded results, which also
gives each client's version, what was exercised and the evidence; CI fails when this column says
otherwise. The latest release is in the README; #187 tracks the clients not verified yet.

How to read them:

- **hidane** is the tree the report is generated from, named by its series (`0.6.x` for the
  workspace version 0.6.0). CI replays the fixtures against it on every pull request and on
  `main`, so on a commit of `main` the replayed answers match. Transcripts are recorded once and
  committed: their evidence carries the date they were last recorded.
- **firebase-tools** is the version the transcripts made under `firebase emulators:exec` ran
  with, as the [SDK certification matrix](sdk-certification.md) knows it; **Official emulator**
  is the release the [Oracle Corpus](oracle-corpus.md) was recorded against.
- **Verified** means the replayed answers, every SDK transcript compared with that release and the
  firebase-tools transcripts all match or differ only as documented, and firebase-tools is
  verified in the SDK certification matrix; otherwise **partially verified**. A combination no
  result covers has no row.

`compatibility.json` holds the same and more: `hidane` (`version`, `series`),
`official_emulator` (the pinned release and its jar's SHA-256), `matrix` (each row with its
evidence: `kind` `replay`, `transcripts` or `firebase-tools`, a count, a description, where it is
documented, when it runs and when it was last recorded), `oracle_corpus` (the manifest's
digest and totals), `replay` (answers per area and per way of comparing them), `transcripts`
(comparisons by result), `sdk_certification` (the clients per status), `browser` (the
firebase-js-sdk suite's outcomes on each emulator, the transcripts made in Chromium),
`functions` (the fixtures of trigger registrations and events, the events each emulator sent),
`integration_tests` (the test files under `crates/*/tests/` and the recordings each replays),
`differential_fuzzing`, and `differences` (the
[difference database](parity-exceptions.md)'s entries by table and by kind: bug-for-bug, more
correct, equivalent, limitation). `schema_version` changes when a field is removed or changes
meaning, not when one is added.

Differential fuzzing has not run yet. A run is reported by writing a summary to
`results/differential-fuzzing.json`, an object whose `runs` each have `name`, `date`, `target`,
`cases`, `differences`, `unexplained` and `evidence` (the file with the cases), and optionally
`official_emulator` (the schema's `fuzzing_run`; list the file in `IGNORED` of
`tools/parity/table.py`). Run `python3 tools/parity/compatibility.py` after
`tools/parity/table.py`, `tools/oracle/corpus.py`, `tools/parity/sdk_certification.py` and
`tools/parity/differences.py`; CI fails while the report is stale.

| FlutterFire `cloud_firestore_web` | Same as firebase-js-sdk in the browser (`firebase_core_web` loads it from `www.gstatic.com/firebasejs/`) | verified in Chromium |
| Emulator UI, `curl`, `firebase-tools` itself | REST and emulator-specific HTTP endpoints | REST and the emulator's endpoints served; Emulator UI v1.15.0 verified (browse, create and delete documents, Clear all data), its request monitor (the Requests tab) since v0.2.1, from the WebSocket feed on `--websocket_port` (#69); `firebase emulators:start` / `emulators:exec` launch hidane through `hidane exec` ([ADR 0006](adr/0006-launch-under-firebase-tools.md)), with the Functions emulator's Firestore triggers (#185): Firestore-triggered functions, v1 and v2 (`withAuthContext` too), receive their events as with the official emulator (#70, `results/functions-triggers-*.json`, differences in [parity-exceptions.md](parity-exceptions.md)); `--import`, `--export-on-exit` and `emulators:export` read and write the official emulator's format, and each emulator reads the other's exports ([export-format.md](export-format.md)) |

So with v0.1 (gRPC only) the server-side SDKs, the mobile SDKs and Node-based test suites work.
The Go, Python and Java server SDKs get the same results from both emulators
(`results/sdk-go-*.json`, `results/sdk-python-*.json`, `results/sdk-java-*.json`, one pair per
section): documents and writes (merges, preconditions, every field transform, a value of each
type, batches, the BulkWriter, listings), queries (filters, `or`, cursors, `limitToLast`,
collection groups, `explain` options), `count` / `sum` / `average`, `findNearest`,
`recursiveDelete` (Python, Java), transactions (read-only, at a past read time, lock waits and timeouts,
retries after `ABORTED`) and listeners on queries, limits, collection groups and documents.
`PartitionQuery` answers `UNIMPLEMENTED` on both. Only the wording of `ALREADY_EXISTS` and
`NOT_FOUND` for a failed precondition differs, as it does for every client
([parity-exceptions.md](parity-exceptions.md)).
Browser apps need WebChannel as well as REST, because the Web SDK does almost everything over
WebChannel. `main` serves both: listeners, writes, queries, batches, long polling and mock tokens
from Chromium give the same results on hidane as on the official emulator
(`results/browser-webchannel-*.json`), and so does firebase-js-sdk's own Firestore browser suite:
the 1,183 tests that run against an emulator pass on both (`tools/js-sdk-browser/`, checked
weekly). Under Security Rules, `@firebase/rules-unit-testing` suites pass the same way in
Chromium and in Node: the same assertions pass, with the same error codes
(`results/browser-rules-*.json`, `results/sdk-rules-unit-testing-*.json`). Denial messages give
the reasons of one evaluation, where the official emulator's also give those of its first pass
and, for a batch, of the writes checked before the denied one ([parity-exceptions.md](parity-exceptions.md)).
A Flutter Web app (`cloud_firestore` 6.10.0, which loads firebase-js-sdk 12.19.0) gets the same
results from both in Chromium: reads and writes of every value type, transforms, queries,
aggregations, `snapshots()` of a query and of a document, a batch, transactions
(`results/flutter-web-*.json`). Only the wording of `NOT_FOUND` for an update of a missing
document differs, as it does for every client ([parity-exceptions.md](parity-exceptions.md)).

## How each client finds the emulator

| Client | Reads `FIRESTORE_EMULATOR_HOST` | Explicit API | TLS |
|---|---|---|---|
| firebase-js-sdk | **No.** Reads `__FIREBASE_DEFAULTS__` (`emulatorHosts.firestore`) at `getFirestore()` | `connectFirestoreEmulator(db, host, port, { mockUserToken })` | disabled automatically |
| firebase-admin (Node) / `@google-cloud/firestore` | Yes (takes precedence over settings) | `settings({ host, ssl: false })` | disabled via the env var path |
| Go | Yes | none (env var only) | insecure credentials automatically |
| Python | Yes | none (env var only) | insecure channel automatically |
| Java | Yes (`setEmulatorHost` takes precedence) | `FirestoreOptions.Builder.setEmulatorHost(host)` | plaintext automatically |
| iOS | No | `useEmulatorWithHost:port:` **only changes the host**; set `settings.isSSLEnabled = false` yourself | manual |
| Android | No | `useEmulator(host, port)` also sets `sslEnabled(false)` | automatic |
| Flutter | No | `useFirestoreEmulator(host, port, sslEnabled: false)` | native: defaults to false; web: delegated to js-sdk |

## Authentication header each client sends to an emulator

| Client | `Authorization` header |
|---|---|
| firebase-admin (Node), Go, Python, Java | `Bearer owner` (treated as administrator) |
| firebase-js-sdk | With `mockUserToken`: an unsigned `alg: none` JWT, or a string token as given (rules-unit-testing's `withSecurityRulesDisabled` passes `owner`). Otherwise the Firebase Auth token, or no header |
| iOS, Android | Only the signed-in user's token, otherwise no header |

The official emulator treats `Bearer owner` and Google OAuth access tokens (`Bearer ya29.…`) as
an administrator, ignoring case. Any other bearer token must be a JWT, which it reads without
verification (any `alg` and signature, no expiry, audience or subject check) for
`request.auth`; a token that is not three URL-safe base64 segments with JSON objects in the
first two fails with `INVALID_ARGUMENT` "invalid jwt", and a header that is not a bearer token
fails with `UNKNOWN` (HTTP 500). Without a header, Security Rules see `request.auth == null`.
Each RPC reads the header after parsing the resource it names and before validating the rest
of the request; Listen and Write read it when the stream opens. hidane follows the same
contract (`tools/oracle/auth.py`).

| Client | Listen stream | Write stream | Commit | BatchGet | RunQuery | RunAggregationQuery | ListCollectionIds | ListDocuments | BeginTransaction | Rollback | BatchWrite | PartitionQuery | ExecutePipeline |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| js-sdk (browser) | WebChannel | WebChannel | REST (transactions) | REST (transactions) | — | REST | — | — | — | — | — | — | REST |
| js-sdk Lite | — | — | REST | REST | REST | REST | — | — | — | — | — | — | REST |
| js-sdk (Node) | gRPC | gRPC | gRPC (transactions) | gRPC (transactions) | — | gRPC | — | — | — | — | — | — | gRPC |
| admin (Node) | gRPC | — | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | — (`new_transaction` on first read) | ✓ | ✓ | — | ✓ |
| Go / Python / Java | gRPC | — | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| iOS / Android | gRPC | gRPC | ✓ (transactions) | ✓ (transactions) | — | ✓ | — | — | — | — | — | — | ✓ |

Notable consequences for the implementation:

- The JS SDKs never call `BeginTransaction`; transactions are `BatchGetDocuments` plus a `Commit` with preconditions. A document read but not written goes into the commit as a `verify` write (`Write.verify`, field 5), which googleapis' published protos lack; the mobile SDKs do the same. Under Security Rules each verify is checked again at the commit, as a `get` of its document (#173).
- The Admin SDK starts transactions lazily with the `new_transaction` option on the first read.
- Mobile SDKs run queries through the Listen stream, not `RunQuery`.
- `PartitionQuery` is only used by the Go / Python / Java clients; the official emulator answers it with 501.
