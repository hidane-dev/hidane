# Migrating from the official emulator

Most projects move their tests from the official Firestore emulator to hidane with two changes:
firebase-tools runs under `hidane exec` ([ADR 0006](adr/0006-launch-under-firebase-tools.md)), and
CI stops installing Java where only the Firestore emulator needed it. `hidane doctor` checks a
project first: what it uses, whether hidane has verified it, and what still needs Java.
`hidane migrate` then shows those changes as a diff, and makes them with `--apply`.

## `hidane doctor`

```sh
hidane doctor                    # the project in the current directory
hidane doctor --path ../my-app   # another directory
hidane doctor --format json      # the findings and the facts behind them, for tools
```

It only reads files: it runs nothing, changes nothing and makes no network request.

| It reads | Where | For |
|---|---|---|
| `firebase.json` (comments allowed, as firebase-tools allows them) | the project, up to four directories deep | the Firestore emulator's host, port and `websocketPort`; the other emulators `firebase emulators:start` starts (decided as firebase-tools 15 decides it) and which of them run on Java; `firestore.edition`; several databases; `emulators.singleProjectMode`; the Emulator UI |
| Security Rules | the files `firebase.json` names | compiled with hidane's compiler, which gives the official emulator's errors and warnings |
| Functions | the `functions` source directories | Firestore triggers: `onDocumentCreated` and the other `onDocument…` functions, `functions.firestore.document(…)`, Python's `on_document_…` |
| SDKs and tools | `package.json` with `package-lock.json`, `npm-shrinkwrap.json`, `yarn.lock`, `pnpm-lock.yaml` or `bun.lock`; `requirements*.txt`, `pyproject.toml` with `poetry.lock`, `uv.lock` or `pdm.lock`; `go.mod`; `pom.xml`, `build.gradle(.kts)`; `pubspec.yaml` with `pubspec.lock` | the versions of `firebase`, `firebase-admin` (and the `@google-cloud/firestore` it resolves to), `@google-cloud/firestore`, `@firebase/rules-unit-testing`, `firebase-tools`, `google-cloud-firestore` (Python, Java), `cloud.google.com/go/firestore`, `firebase-firestore` (Android), `cloud_firestore` (Flutter, with its platform directories) |
| CI | `.github/workflows/*.yml` | the steps that start the emulators, directly or through npm scripts and the shell scripts they run; `actions/setup-java` and what else in the job needs Java; `FIRESTORE_EMULATOR_HOST`; caches of `~/.cache/firebase/emulators` |
| Scripts | npm scripts, and shell scripts that workflows and npm scripts run | `firebase emulators:exec` and `emulators:start`, run directly, through `npx`, `pnpm exec`, `yarn` or `bunx`, after environment assignments, in `&&` chains |

### Findings

Each finding has a status:

| Mark | Status | Meaning |
|---|---|---|
| ✓ | `compatible` | Verified with hidane. The finding names its source: a document or a result file in this repository |
| ~ | `likely-compatible` | The same major version as a version verified with hidane, but not that version itself; the finding names the verification. Not an incompatibility |
| ✓ | `ok` | A check that passed and claims nothing about verification (`firebase.json found`) |
| · or ! | `info` | Information; `!` (severity `warning`) when it asks for something, such as keeping Java for another emulator |
| ? | `unknown` | Nothing hidane has verified covers it: manual verification required |
| ✗ | `incompatible` | A known gap, or something that will not work under hidane as it is |

A package's version is judged against the version hidane was verified with:

- `compatible` when the version the project uses is known (resolved by a lockfile, or pinned
  exactly, such as `"firebase-tools": "15.33.0"` or `google-cloud-firestore==2.34.1`) and has the
  verified version's major and minor versions; only the patch version may differ;
- `likely-compatible` when only the major version is the same, or when a range pins that major
  version but the version it resolves to is not known (`^13.0.0` without a lockfile);
- `unknown` otherwise.

`firebase-admin` is judged by the `@google-cloud/firestore` its lockfile resolves to; without a
lockfile it is not verified. Firestore triggers are judged by the `firebase-functions` of their
functions; triggers written in Python are not verified. The mobile SDKs and Flutter on Android,
iOS, macOS and Windows are not verified yet ([compatibility.md](compatibility.md)). A version
range that does not pin a major version (`>=2.20`, `*`) is `unknown`. The Emulator UI's version
is the one firebase-tools pins (v1.15.0 for firebase-tools 15.33.0), so it is judged as the
project's firebase-tools is.

Known gaps are `incompatible`:

- The enterprise edition (`firestore.edition: "enterprise"`): queries are answered as on a
  standard database, where the official emulator answers them with other semantics
  ([#338](https://github.com/hidane-dev/hidane/issues/338)), and pipelines are not implemented
  yet ([#80](https://github.com/hidane-dev/hidane/issues/80)).
- Datastore mode, through `gcloud emulators firestore start --database-mode=datastore-mode`
  ([#81](https://github.com/hidane-dev/hidane/issues/81)). A Datastore client library in the
  dependencies is `unknown`: it may talk to the separate Datastore emulator, which hidane does
  not replace.
- A rules file that does not compile: hidane would start without it. hidane's compiler makes the
  official emulator's checks (`crates/hidane/tests/fixtures/rules_compile.json`), so the official
  emulator most likely rejects the file too; if it does not, please report it.

What still needs Java is information, not a gap: the Realtime Database, Storage and Pub/Sub
emulators run on Java, and under `hidane exec` firebase-tools runs them with the Java on `PATH`.
A CI job keeps `actions/setup-java` when one of them starts, when it runs another Java command
(`./gradlew`, `mvn`, `java`), or when `setup-java` caches a Java build.

`hidane doctor` exits with 0 when no finding is incompatible, 1 when one is, and 2 for a usage
error or a path that is not a directory. `likely-compatible` and `unknown` findings do not change
the exit code.

### JSON

`--format json` prints the report as one object: `schema` (`hidane.doctor/1`, which changes when
the shape does), `hidane` (the version that wrote it), `summary` (the count of each status: `compatible`, `likely_compatible`, `ok`, `info`, `unknown`,
`incompatible`),
`findings` (each with `code`, `group`, `status`, `severity`, `title`, and when they apply
`details`, `source`, `file` and `line`; paths are relative to the project) and `facts` (what the
scan read: `firebase`, `rules`, `functions`, `dependencies`, `emulator_commands`, `workflows`,
`scripts`, and `unread`, the places that start the emulators in a way the scan could not read).
The engine behind it is the `hidane::project` module, which reads a directory or files held in
memory.

## `hidane migrate`

```sh
hidane migrate                   # what would change, as a diff; changes nothing
hidane migrate --apply           # make the changes
hidane migrate --format patch    # only the diff, for `git apply`
hidane migrate --format json     # the plan, for tools
```

`hidane migrate` reads the project as `hidane doctor` does, without the network. Without
`--apply` it changes nothing: it prints what it detected, the suggested changes and their diff,
what it leaves as it is, and the command that applies them.

In GitHub Actions, hidane is installed with the
[`hidane-dev/setup-hidane`](https://github.com/hidane-dev/setup-hidane) action: `@v1` follows the
latest 1.x release, and its `version` input picks a hidane version.

### What it changes

Only patterns it recognises, as little as possible, editing the text in place so that comments
and layout stay:

| Where | Before | After |
|---|---|---|
| A workflow `run` step in bash or sh, an npm script, or a shell script that one of them runs | `firebase emulators:exec …` or `emulators:start …`, run directly or through `npx`, `pnpm exec`, `yarn` or `bunx`, after `VAR=value`, in a `&&` chain | the same command after `hidane exec -- ` |
| A job that starts the emulators that way and needs Java for nothing else | `uses: actions/setup-java@…`, its `with` inputs, a step name that mentions Java | `uses: hidane-dev/setup-hidane@v1` |
| A job where something else still needs Java (another emulator, `./gradlew`, `mvn`, setup-java's build cache, a matrix of Java versions), or where that is not known | `actions/setup-java` | kept, and `- uses: hidane-dev/setup-hidane@v1` added after it |
| A job without setup-java | | `- uses: hidane-dev/setup-hidane@v1` added before the step that starts the emulators |

A job whose only Java was for the Firestore emulator:

```yaml
# Before
      # firebase-tools 15 needs Java 21 to run the Firestore emulator.
      - name: Set up Java
        uses: actions/setup-java@v4 # v4.7.1
        with:
          distribution: temurin
          java-version: "21"
      - run: npm ci
      - run: npx firebase emulators:exec --only firestore "npm test"
```

```yaml
# After
      # firebase-tools 15 needs Java 21 to run the Firestore emulator.
      - name: Set up hidane
        uses: hidane-dev/setup-hidane@v1
      - run: npm ci
      - run: hidane exec -- npx firebase emulators:exec --only firestore "npm test"
```

A job that also starts the Storage emulator keeps its Java:

```yaml
# After
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: 21
      - uses: hidane-dev/setup-hidane@v1
      - run: |
          hidane exec -- firebase emulators:exec "npm test" \
            --project demo-storage-auth
```

An npm script:

```json
"test:emulator": "firebase emulators:exec --only firestore 'npm test'"
```

```json
"test:emulator": "hidane exec -- firebase emulators:exec --only firestore 'npm test'"
```

A command already under `hidane exec`, or a job that already uses `hidane-dev/setup-hidane`, is
left as it is, so a second run changes nothing.

### What it leaves to you

Each of these is listed under "Left as it is", with the reason:

- `FIRESTORE_EMULATOR_HOST`: it stays as it is, since under `hidane exec` hidane listens on the
  host and port firebase-tools gives it, from `firebase.json`.
- Dependencies and lockfiles: npm scripts that now run `hidane` need it installed
  (`npm install --save-dev hidane`, or another channel in the [README](../README.md#install)).
- Commands it could not read with confidence: in a quoted string (`bash -c "…"`), started by
  another tool (`concurrently "firebase emulators:start" …`), by a container action, in a
  Makefile, in PowerShell or on a Windows runner (where `hidane exec` is not verified), and
  `gcloud emulators firestore start`.
- setup-java steps with a key or an input it does not know (`id`, `cache`, …), several of them
  in one job, or one after the step that starts the emulators.
- A workflow that pins its actions by commit SHA: pin `hidane-dev/setup-hidane` the same way.
- Caches of `~/.cache/firebase/emulators`: firebase-tools no longer downloads the Firestore
  emulator there, but still the Emulator UI and other emulators.

### `--apply`

1. Each file is checked to be the one the plan was made from.
2. Unless `--force` is given, git is asked whether any of the files has uncommitted changes
   (untracked files included); if one has, nothing is written. Outside a git work tree it says
   that it could not check.
3. Each file is copied to `.hidane-backup/<UTC time>/<path>` in the project. Delete the directory
   once the changes are reviewed, or add it to `.gitignore`.
4. Each file is written atomically: a temporary file in the same directory, with the file's
   permissions, renamed over it.
5. A second plan is made, which must find nothing to change; if it does, it says so.

`hidane migrate` exits with 0 when the plan was printed or applied (or there was nothing to
change), 1 when `--apply` refused or failed, and 2 for a usage error or a path that is not a
directory.

### JSON

`--format json` prints the plan: `schema` (`hidane.migrate/1`), `hidane`, `detected` (the emulator
commands and setup-java steps it found, each with `file`, `line` and `what`), `files` (for each
file: `file`, `blob`, the git blob id of the file the plan was made from, `changes` with `code`,
`line` and `description`, `diff`, and `after`, the whole new text), `notes` (findings, as in
`hidane doctor`) and `patch` (every diff). With `--apply`, `applied` lists the files written and
the backup directory. A tool that holds a copy of the repository can check `blob` against its
copy before writing `after`. The engine behind it is the `hidane::migrate` module.

## Opening the migration as a pull request

The [`hidane-dev/setup-hidane/migrate`](https://github.com/hidane-dev/setup-hidane#migrating-to-hidane-in-a-pull-request)
action runs `hidane migrate` in GitHub Actions and opens its changes as a pull request. It is
opt-in: it runs in a workflow someone starts by hand in their own repository, never on a schedule
or on any other event.

```yaml
name: Migrate to hidane

on:
  workflow_dispatch:

permissions:
  contents: write
  pull-requests: write

jobs:
  migrate:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@v7
        with:
          persist-credentials: false
      - uses: hidane-dev/setup-hidane/migrate@v1
```

It makes the plan with `--format json` from the tip of the base branch, and stops when there is
nothing to change. Otherwise it applies the plan with `--apply` on a new branch
(`hidane/migrate-<commit>`), commits exactly the files hidane wrote (not `.hidane-backup/`), pushes
that branch, which must not exist yet, and opens a draft pull request whose description is the
plan: the changes, what it leaves to you, the diff, and `hidane doctor`'s report on the branch.
`dry-run: true` shows that description without pushing anything.

The workflow's `GITHUB_TOKEN` cannot push changes to `.github/workflows/`, and the pull requests it
opens start no workflow; the action's README shows how to give it a GitHub App token or a
fine-grained personal access token instead. The action needs a hidane release with
`hidane migrate`, that is, 0.5.0 or newer.

### One engine

`hidane migrate`, the action and any later integration make the same changes, because they share
one engine: `hidane::migrate::plan` makes the plan from a project's files (a directory, or files
held in memory, through `hidane::project::files::Tree`), and `hidane::migrate::apply` writes it.
The action reads the plan as JSON (`hidane.migrate/1`) and edits nothing itself. A GitHub App, if
one comes later, would call the same `hidane::migrate::plan` on a repository's files and open the
same pull request, so that what it proposes is what `hidane migrate` shows locally.
