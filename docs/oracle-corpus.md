# Hidane Oracle Corpus

The Hidane Oracle Corpus is every recording of the official Cloud Firestore emulator that hidane
keeps: the answers its tests replay, and the SDK transcripts compared with hidane's. The
recordings stay where the tests read them, in `crates/*/tests/fixtures/` and `results/`. What
makes them a corpus is a manifest that lists each one with its provenance and with how its answers
are compared:

| File | What it is |
|---|---|
| [`oracle-corpus.json`](oracle-corpus.json) | The manifest, generated by [`tools/oracle/corpus.py`](../tools/oracle/corpus.py) |
| [`oracle-corpus.schema.json`](oracle-corpus.schema.json) | Its JSON Schema (draft 2020-12) |

`python3 tools/oracle/corpus.py` writes the manifest; CI runs it with `--check`, which fails when
the manifest is stale or does not fit the schema, as it fails for the parity table
([`parity.md`](parity.md)).

The manifest lives in `docs/`, next to `parity.md`, which is generated from the same recordings,
and next to this page. A top-level `oracle/` directory would suggest the recordings live there;
they do not move, since each test reads its own.

## What is in it

| Kind | Files | Made by | Used by |
|---|---|---|---|
| `fixture` | `crates/*/tests/fixtures/*.json`, and `results/rules-conditions-official-v1.22.0.json` | A script in `tools/oracle/` that talks to the official emulator directly (REST, gRPC through `grpcurl` or `@grpc/grpc-js`, WebChannel, WebSocket, or by starting the jar) | A test that replays its answers against hidane and compares them, as `tools/parity/table.py` counts them |
| `transcript` | `results/<name>-official-v<version>.json` | A script that runs the same steps through an SDK (`tools/oracle/sdk_*.mjs`, `sdk_go/`, `sdk_python/`, `sdk_java/`, `webchannel/`, `flutter_web/`, `functions/`, `tools/js-sdk-browser/`) | Compared, as a whole, with the transcript of the same steps against hidane (`results/<name>-hidane.json`) |

Every recording in it was made against `cloud-firestore-emulator` v1.22.0. The manifest's
`totals` give the counts: files, fixtures, transcripts, answers, bytes, and these per area, per
release and per way the release is known.

## Structure

The manifest is one JSON object:

| Field | What it holds |
|---|---|
| `schema_version` | The version of this format (below) |
| `digest` | `sha256:` and the SHA-256 of the lines `<sha256>  <path>` of every recording, sorted by path: it names the corpus's content exactly |
| `releases` | Each official emulator release the recordings were made against, its jar's SHA-256, and whether it is the one `.github/actions/official-emulator/pinned.sh` pins (`pinned`) |
| `totals` | `files`, `fixtures`, `transcripts`, `answers`, `bytes`, `levels` (answers per way of comparing), and `fixtures`, `transcripts` and `answers` `by_area`, `by_release` and `by_release_source` |
| `recordings` | One entry per recording, fixtures first, each list in the parity table's order |

An entry:

| Field | What it holds |
|---|---|
| `path`, `kind`, `area` | The file, `fixture` or `transcript`, and its area in the parity table |
| `recorder` | The script (or directory) that made it: its `generated_by` header, else the table of [`tools/oracle/README.md`](../tools/oracle/README.md); for a transcript, the script that prints it |
| `client.over` | The official emulator's interfaces the recorder used: `gRPC`, `REST` (any HTTP/1.1 request: the REST API and the emulator's own endpoints), `WebChannel`, `WebSocket`, `process` (the jar itself: its flags, what it prints, its exit code, the files it writes), `CLI` (firebase-tools commands) |
| `client.using`, `client.packages` | What the recorder used, and the packages it used, each with its version and where that comes from: `pinned` (the file in `where` pins it: `go.mod`, `requirements.txt`, `pom.xml`, `pubspec.yaml`, the js-sdk-browser workflow), `recorded` (the transcript states it), `unpinned` (the script installs the release current when it is run; the version is not known) |
| `oracle` | `release`, the jar's SHA-256 where known, and `source`: how the release is known (below) |
| `recorded` | `first_recorded` and `last_changed`, dates from git history (below) |
| `bytes`, `sha256` | The file's size and SHA-256 |
| `answers`, `levels`, `replayed_over`, `tests`, `counted`, `compared` | Fixtures: how many answers the tests replay, how many at each level of comparison ([`parity.md`](parity.md) says what each means), the transports the replay uses, the test functions, what one answer is, and what is compared |
| `compared_with` | Transcripts: each transcript compared with it (hidane's, and for export and import each emulator reading the other's export), and the result: `identical`, `documented` (with the file that explains the difference) or `unexplained` |

### How a release is known

| `oracle.source` | Rule |
|---|---|
| `header` | The recording's `oracle` field, `cloud-firestore-emulator v<version> (sha256 <jar>)`, which its script writes |
| `file name` | `-official-v<version>.json`; the jar's SHA-256 is not stated (`null`) |
| `git history` | A fixture with neither. Its release is the single one `tools/oracle/` names where the file's content was made: at the commit that last changed it (`git log -- <path>`, then `git grep` at that commit), or in the working tree for a change not committed yet. `evidence` says so, and whether the commits that changed it before named the same release. The repository has named no release other than v1.22.0 |

### Dates

`first_recorded` and `last_changed` are the dates of the first and the last commit that changed
the file, in the time zone each commit was made in, or today's date for a change not committed
yet. `last_changed` is not always a new recording: git does not tell a recording made again from
a hand edit of the file, such as a `compare` mark.

These fields, and a release found in git history, are kept as they are while the recording's
SHA-256 is unchanged. `--check` therefore needs no history (CI checks out a single commit), and a
squash merge, which gives the commit a new date, does not make the manifest stale. When a
recording changes, `python3 tools/oracle/corpus.py` takes them from git again.

## Adding a recording

1. Write the recorder, or extend one, in `tools/oracle/`, following
   [the observation policy](clean-room/OBSERVATION_POLICY.md). A fixture that is a JSON object
   starts with `"oracle"` and `"generated_by"`, as the other scripts write them; give the script a
   row in the table of `tools/oracle/README.md`.
2. Record against a freshly started official emulator of the pinned release, under an English
   locale, and write the test that replays the recording.
3. Add the fixture to `RECORDINGS` in `tools/parity/table.py` (a transcript pair to `TRANSCRIPTS`),
   and run `python3 tools/parity/table.py`.
4. Run `python3 tools/oracle/corpus.py`. A new recorder needs a line in `FIXTURE_CLIENTS` (the
   interfaces it uses); a transcript recorder that is not `tools/oracle/sdk_<name>.mjs`, one in
   `TRANSCRIPT_RECORDERS`; a recorder that pins a package, one in `PINS`. The script says which.
5. Commit the recording, `docs/parity.md` and `docs/oracle-corpus.json` together.

## Versions

- **The format** has `schema_version`. Adding a field does not change it; removing a field or
  changing what one means does, with the schema.
- **The content** is named by `digest`, and by the release it records. The corpus has no version
  number of its own: each hidane release tag fixes the recordings and the manifest that lists them.
- **One official release at a time.** A new official release re-records everything. When
  firebase-tools pins a newer emulator, the `newer` job of the Official emulator workflow fails
  ([`tools/oracle/README.md`](../tools/oracle/README.md#the-official-emulator-in-ci)); then
  every script's `oracle` constant and `pinned.sh` change to the new release, every fixture and
  official transcript is recorded again against the new jar (the transcripts under their new
  name, `-official-v<new>.json`), hidane changes where the answers changed, and
  `docs/parity-exceptions.md`, `docs/parity.md` and the manifest follow. A fixture without a
  header then gets the new release from git history (its `evidence` noting that earlier commits
  named v1.22.0); while `tools/oracle/` names two releases, `corpus.py` refuses to place such a
  fixture, so a half-finished move does not pass.
- **A second release next to v1.22.0**, should hidane ever need to match two (for projects pinned
  to an older firebase-tools): its recordings would sit beside the first ones under a name that
  carries the release (`queries-v1.23.0.json`, `results/<name>-official-v1.23.0.json`), each
  with its `oracle` header; `RECORDINGS` and `TRANSCRIPTS` would list both, the tests would
  replay each against the behaviour hidane gives that release, and the manifest would list both
  releases, `pinned` marking the one new recordings are made against, with `totals.by_release`
  counting each. The format already allows it; the tests' layout would change when it is needed.

## Sanitisation

A recording is published with the repository. The
[observation policy](clean-room/OBSERVATION_POLICY.md#what-a-recording-may-hold) says what it may
hold; in short:

- synthetic data only: project IDs the script chooses, documents it writes, unsigned mock tokens
  and `Bearer owner`; no real project, user or application data;
- no credentials of any kind;
- what changes from run to run masked (`<time>`, `<id>`, `<token>`, `{project}`), and no path or
  other detail of the machine it was made on (`{dir}`); check with
  `grep -nE '/(Users|home)/' <file>` before committing;
- nothing from inside the jar, and no more of a page or script the emulator serves than the test
  compares.

## As a behavioural specification

Each fixture holds requests and the official emulator's answers to them; its entry says what one
answer is (`counted`), what of it is compared (`compared`, `levels`) and which test replays it.
Together they describe the official emulator's behaviour area by area, in a form any
implementation can be checked against: send the recorded requests, compare the answers as the
entry says. Where hidane departs from it on purpose, the answers are marked (`differs` and the
other `compare` marks, the lists a test keeps) and [`parity-exceptions.md`](parity-exceptions.md)
says why. The transcripts add the same at the level of an SDK's API.

It specifies what was observed, and only that: one release, the cases each script chose, summaries
where a recording keeps a summary rather than the whole answer, and timing compared loosely where
it varies from run to run. A behaviour no recording covers is not specified by the corpus.
