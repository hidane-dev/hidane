# Parity exceptions

hidane treats the official Cloud Firestore emulator as the oracle: its answers are recorded
(`tools/oracle/`) and replayed against hidane by the test suite, and the differences are
published. This page lists the places where hidane
**intentionally** behaves differently, and the places where the official emulator itself
diverges from production Firestore so that a parity target has to be chosen.

Status: kept up to date with each change. Naming, for each entry, the fixture or test that pins
hidane's side is #45.

The tables are generated from a database, [`parity-exceptions.json`](parity-exceptions.json)
([schema](parity-exceptions.schema.json)), which holds each entry with structured fields:

| Field | What it holds |
|---|---|
| `id` | A stable ID, `D001`, `D002`, …, shown in the Kind column. A new entry takes the next one; an ID is never reused |
| `table`, `area`, `topic` | The table it is in, its area in the [parity table](parity.md), and, in the second table, its Area column |
| `official` | What the official emulator does |
| `firestore` | What production Firestore does, where the entry knows it (the second table's Production column, or what an entry of the first table says of production); `null` where nothing recorded says, since production is not observed yet (#82) |
| `hidane` | What hidane does |
| `reason` | Why: the first table's Why column, the second table's Decision column |
| `kind` | `bug-for-bug`: hidane does what the official emulator does, where production differs. `more-correct`: hidane departs from the official emulator to do what production or the documented contract does, or to fix what is a bug whatever production does. `equivalent`: hidane departs in a detail clients do not observe or cannot rely on (wording, transport, timing, order, opaque formats), with the same outcome. `limitation`: hidane departs because it does less, or bounds what the official emulator does not |
| `references` | The issues (`hidane-dev/hidane#86`, `firebase/firebase-tools#11241`), web pages and repository files the entry relies on: at least every one its text mentions, and more where useful, such as the fixture that pins hidane's side |

To add or change an entry, edit the database and run `python3 tools/parity/differences.py`,
which validates it, checks that every reference its text makes is listed and that each file
exists, and writes the tables below; CI runs it with `--check`. The database lives next to this
page rather than as one file per entry under a new directory: one file keeps the entries in the
order the tables show, reviews as one diff, and validates against one schema, as the
[Oracle Corpus](oracle-corpus.md) manifest does, and this page keeps its address, which the
documentation and `tools/parity/table.py` refer to.

| Area | Official emulator | Production Firestore | Decision | Kind |
|---|---|---|---|---|
| Transactions | Locks, measured in #17: a read-write transaction holds a shared lock on every document it reads (found or not) and on every collection with a collection ID it lists or queries, whatever the parent. A write, in a transaction or not, waits for other transactions' locks for up to 2 s, then fails with `ABORTED` "Transaction lock timeout." (which ends a waiting transaction). An unused transaction expires 60 s after its last request (the [docs](https://docs.cloud.google.com/firestore/native/docs/emulator) say 30 s). `concurrency_mode: OPTIMISTIC` is accepted and ignored. Read-only transactions lock nothing and read the snapshot of their start | Contention is resolved by aborting a transaction with `ABORTED` rather than by a fixed wait, and optimistic concurrency can be selected | Follow the official emulator: same lock scope, waits, expiry and messages (`tests/fixtures/transactions.json`, replayed by `crates/hidane/tests/transactions.rs`) | bug-for-bug (D069) |
| Composite indexes | Not tracked or required | Required for many queries | Follow the emulator (no index enforcement) | bug-for-bug (D070) |

## Not in scope (neither emulator nor hidane)

- `google.firestore.admin.v1` (index, field, database, backup management): the official emulator does not expose it. hidane answers `UNIMPLEMENTED`.
- TTL, point-in-time recovery, bundles: no emulator support.
- Realtime Database, Cloud Storage, Auth emulators.

## How to read the parity table

The parity table, [parity.md](parity.md), is generated from the recorded fixtures by
`tools/parity/table.py`: per area and transport, how many official answers the tests replay and
how each test compares them (in full, decision and reasons, in part, status only). An answer
that a recording marks (`differs`, a `compare` of `status`, `codes` or `none`) or a test lists
(`KNOWN`, `FIRST_LINE_ONLY`, `CRASHES`) as different is one where hidane intentionally answers
differently, and a row of the first table above says why; a Security Rules denial compared on
its decision and reasons follows from evaluating conditions once. The table counts these rows
too.
