# SDK certification matrix

Which clients and tools hidane has been verified with, at which version, over which transport,
on what, and on which evidence. Every row comes from the recorded results in
[`results/`](../results/README.md) and nothing else: a client is never marked verified without a
transcript of it run against both hidane and the official emulator.

| File | What it is |
|---|---|
| [`sdk-certification.json`](sdk-certification.json) | The matrix, generated by [`tools/parity/sdk_certification.py`](../tools/parity/sdk_certification.py) |
| [`sdk-certification.schema.json`](sdk-certification.schema.json) | Its JSON Schema (draft 2020-12) |

`python3 tools/parity/sdk_certification.py` writes the matrix, the table below, the table of
verified versions in [migrating.md](migrating.md) and `VERIFIED` in
`crates/hidane/src/project/verified.rs`, the versions `hidane doctor` judges a project's
dependencies against. CI runs it with `--check`, which fails when any of them is stale, when the
matrix does not fit its schema, or when the status column of [compatibility.md](compatibility.md)
says something else. So the doctor, the documentation and the matrix cannot disagree.

## How a row is made

- **Evidence**: the transcript pairs in `results/` (`<name>-official-v<version>.json` and
  `<name>-hidane.json`), the same steps run through the client against each emulator.
  [`tools/parity/table.py`](../tools/parity/table.py) compares each pair: identical as JSON, a
  difference the documentation explains, or unexplained. [oracle-corpus.json](oracle-corpus.json)
  says which official emulator release each was recorded against.
- **Exercised**: what a transcript exercised, per client, is declared in the script (`EVIDENCE`),
  and each declared feature must show in the names of the transcript's steps (a suite's passed
  tests; for export, import and the launch under firebase-tools, in the transcript's row in
  `results/README.md`). A feature no step names cannot be claimed.
- **Version**: the version of the client's package the transcripts ran with, known in one of
  three ways: *recorded* in the transcript itself, *pinned* by the script that made it (`go.mod`,
  `requirements.txt`, `pom.xml`, `pubspec.yaml`, the js-sdk-browser workflow), or *stated* for that
  transcript by its row in `results/README.md`. A transcript none of these gives a version for
  counts as evidence of what was exercised but not of the version. Two versions of one package
  across a client's transcripts stop the script: record them again with one version, or give each
  its own row.
- **Status**:
  - **Verified**: every feature the client is expected to offer (`core`: for an SDK, documents and
    writes, queries, aggregation queries, transactions and listeners, where it has them) was
    exercised by a pair that is identical or differs only as the documentation explains, and the
    version is known.
  - **Partially verified**: recorded results cover the client, but a core feature was not
    exercised, the version is not known, or a difference is unexplained. The row says which.
  - **Not verified**: no recorded result covers it. hidane may serve its transport
    ([compatibility.md](compatibility.md)); nobody has compared its results yet.
- **Dates**: `last_recorded` is the latest date one of the client's hidane transcripts was
  recorded: the date of the last commit that changed the file, kept while the file is unchanged,
  as [the corpus](oracle-corpus.md#dates) keeps its dates.

A verified client is verified at that version, for what was exercised, against that official
emulator release. Other versions are judged by `hidane doctor` as [migrating.md](migrating.md)
says: the same major and minor version is `compatible`, the same major version
`likely-compatible`, anything else not verified.

## Adding or changing a client

1. Record its transcripts against both emulators with a script in `tools/oracle/`, and add the pair
   to `TRANSCRIPTS` in `tools/parity/table.py` and a row to `results/README.md` that states the
   version of the client it ran (or record the version in the transcript, or pin it in the
   script).
2. Run `python3 tools/parity/table.py` and `python3 tools/oracle/corpus.py`.
3. Say what the transcript exercised, per client, in `EVIDENCE` of
   `tools/parity/sdk_certification.py` (a new client also needs a row in `CLIENTS`), and run it.
   It fails until every transcript has an entry, and while a claimed feature does not show in the
   transcript.
4. Update the status column of [compatibility.md](compatibility.md) if the script says so, and
   commit the transcripts and every generated file together.

## For tools

The matrix is for programs too: an upstream watcher can compare each row's `ecosystem`,
`package` and `version` with the latest release of that package, and `hidane doctor` reads the
same versions (`verified_packages`). The fields:

| Field | What it holds |
|---|---|
| `statuses`, `features` | The statuses and the features, with their labels |
| `totals` | The number of rows, and of rows with each status |
| `clients[].id`, `client`, `ecosystem`, `package`, `platform`, `transport` | The row: a stable ID, its name, its package (`npm`, `pypi`, `go`, `maven`, `pub`, `swiftpm`, `other`) and the transports it uses against an emulator |
| `clients[].status`, `version`, `official_emulator` | The status, the version the recorded results ran (`null` when none states it), and the official emulator releases they were compared with |
| `clients[].core`, `exercised`, `not_exercised`, `gaps` | The features that make it verified, those exercised, those missing, and every reason it is not verified in full |
| `clients[].evidence[]` | Each transcript pair: `transcript` (its name in `table.py`), `official`, `official_emulator`, `official_recorded`, `compared` (each transcript compared with the official one, with its result, SHA-256 and dates), `result` (the worst of them), `packages` (each with `version` and `source`: `recorded`, `pinned`, `stated` or `unknown`) and `features` |
| `clients[].last_recorded`, `tracking` | The latest date of its hidane transcripts, and the issue that tracks verifying it |
| `verified_packages[]` | What `hidane doctor` judges against: each package with a verified row, its version, what was verified, and the rows behind it |

`schema_version` changes when a field is removed or changes meaning, not when one is added.
